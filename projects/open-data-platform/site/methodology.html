Methodology

Every release should be explainable from source bytes to customer file.

The platform separates source acquisition, normalization, logical product state, immutable release identity, distribution formats, operational evidence, and commercial approval instead of hiding them behind one opaque export.

Release model

Database → Product → Release → Distribution

1. Preserve the source

Source payloads are archived immutably with source-native identifiers, hashes, provenance, and source-version evidence.

2. Build a logical product

Normalization and product rules are deterministic. Product identity is not tied to whichever file format a customer happens to download.

3. Publish immutable releases

A release binds the exact information state, manifests, schemas, configuration, quality evidence, provenance, licensing notices, changelog, and checksums.

Equivalent distributions

One verified information state can travel in several formats.

SQLite

Canonical local queryable state for products that benefit from indexes and immediate SQL access.

CSV and Parquet

Convenient distributions for interoperability and analytical pipelines. A new file format does not create a new logical release by itself.

History

Changes are evidence, not guesses.

Historical products require verified source states and verified adjacent change artifacts. Missing history is not inferred from version numbers, changelog prose, or the latest source dump.

A later source release never silently changes an already published commercial bundle. Corrections or new information create a new release identity.
Commercial boundary

Technical readiness and legal approval remain independent.

Software proves

  • candidate integrity
  • source/product/history evidence
  • exact file hashes
  • product-scoped approval references
  • immutable sale-envelope bindings

Humans decide

  • customer-terms wording
  • legal sufficiency
  • license-plan boundaries
  • warranty/liability/governing-law language
  • whether redistribution requires different terms
Identity

Names and paths are not permanent identity.

Long-lived platform objects use stable internal identities. Source-native IDs are preserved. Cross-database relationships belong in separate versioned mapping layers rather than destructively merging source records.
